

### plan.md
# BENCH-MODEL-001 / T1 — Implementation plan

## 1. Scope and design constraints

Deliver one governed application, but preserve three separate authority planes:

1. **OpenJM operator control plane:** OpenJM staff manage tenant lifecycle, entitlements, connector/platform configuration and platform-wide policy. Operators may see per-tenant usage and operational metadata, but must not read customer content. (Contractual; tenant suspension, credential rotation and usage visibility are required.)
2. **Customer organisation administration plane:** customer admins manage only their tenant's users, groups, data sources and permissions. Their operations are tenant-scoped and audited; access changes must be deliberate and reversible.
3. **End-user experience:** employees ask questions and receive answers with source traceability and an explicit uncertainty response where confidence is insufficient. This plane must not expose administration functions or bypass authorization.

**Existing baseline:** tenant claim plus application-enforced row scoping and tests; tenant-specific Keycloak realms, OIDC/PKCE and viewer < analyst < admin roles; workspace membership; internal/confidential document classification; PDF/DOCX ingestion up to 25 MB; object storage; whole-document PostgreSQL full-text retrieval; JSON REST connector; append-only write/privileged-read audit; structured logs, latency/error metrics and failed-job alert; CI build/tests/container/signed release. Do not represent embeddings, vector search, reranking, fine-grained ACLs, a managed LLM gateway, source-system connectors, or an approval workflow as existing.

Change labels used below: **[CONFIG]** existing capability/configuration; **[EXTEND]** change to an existing service or control; **[NEW]** capability to build; **[DECISION]** an unresolved product/security choice that must be decided before implementation, not silently assumed.

## 2. Functional requirements

- **[EXTEND] Operator functions:** tenant suspend/resume, entitlement and platform-policy administration, connector lifecycle and credential rotation, and per-tenant usage views. Enforce operator/customer role separation in APIs and UI; operator content access is denied by design, including through logs, debugging and support tooling. Suspension blocks new access and work while preserving tenant data for authorized export/deletion workflows.
- **[EXTEND] Customer admin functions:** tenant-local user/group administration and group-to-role assignment through the existing realm/role model; workspace and source configuration; assignment of workspaces and supported source scopes to groups; review/revoke access; and audited, reversible changes. Reject cross-tenant object identifiers even when supplied directly to APIs.
- **[NEW] Governed source query path:** provide read-only question answering over approved ERP, warehouse, PostgreSQL and SQL Server data. Translate a question to a constrained query plan, validate it against an admin-approved schema/catalog and caller's authorized scope, then execute through a least-privilege source identity with bounded runtime/result size. Do not permit generated writes, DDL, arbitrary procedures or unrestricted source browsing. A safe refusal is preferable to unapproved query execution.
- **[EXTEND] Knowledge Q&A:** preserve current document upload/search behavior while adding permission-aware evidence retrieval, answer generation, source references and a calibrated abstention/uncertainty response. Every answer a user can act on must link to source records/documents and identify the evidence used.
- **[NEW] Source administration:** show connection/sync health and last successful sync, allow authorized configuration changes and pause/resume, and provide a tenant export and deletion request/status workflow consistent with the 30-day deletion commitment.

## 3. Nonfunctional requirements

- **Performance — [DECISION]/[NEW]:** establish workload and SLO targets (interactive latency, ingestion freshness, query timeout, concurrency and answer token limits) before sizing. Instrument latency by tenant and stage (source fetch, extraction, retrieval, LLM, response), then load-test representative source sizes. Use bounded pagination, incremental sync where source capabilities allow, back-pressure and per-tenant quotas. Do not claim an SLA or target not stated in FACTS.
- **Cost — [NEW]:** meter per-tenant source bytes/rows, jobs, storage, retrieval and LLM calls/tokens; expose aggregate usage to operators without content. Set configurable quotas/alerts and cap query/result/LLM budgets. **[DECISION]** Entitlement and chargeback limits need business values. Avoid sending full source tables or complete documents to the LLM; send only authorized, bounded evidence.
- **Availability — [EXTEND]:** preserve service availability through connector/LLM outages with bounded retries, job retries and clear stale-data status; interactive requests fail closed if authorization cannot be checked. Define recovery objectives and dependency availability targets as a release decision because FACTS provides no SLO/RPO/RTO. Avoid a connector outage blocking other tenants.
- **Privacy and security — [EXTEND]/[NEW]:** enforce region placement for stored tenant content, indexes, backups and processing; no cross-tenant training or retrieval. Model-provider calls currently use per-provider API keys and no managed gateway exists. Before using a provider, verify contractual data handling, region, retention/training settings and available endpoint; add a region-aware provider adapter and secret rotation/least-privilege controls as new work if existing integrations do not meet these constraints. Never send unauthorized content to a model. Minimize content in logs and metrics.
- **Operability — [EXTEND]:** retain structured logs, latency/error Prometheus metrics and failed-job alerts; add connector-specific sync lag/failure, source throttling, ingestion backlog, stale index, authorization-denial, LLM timeout/error, per-tenant usage and deletion/export progress metrics. Correlate events with tenant and request/job IDs without logging document bodies, prompts or credentials. Add runbooks and operator/customer-facing health status.

## 4. Data ingestion and connectors

- **Connector inventory:** the REST JSON connector exists. ERP (SAP/NetSuite/Dynamics), data warehouses (Snowflake/BigQuery/Redshift), SQL Server and object-storage connectors are **[NEW]**; PostgreSQL source connectivity is also **[NEW]** (the deployed PostgreSQL is the application database, not evidence of an external-source connector). Build a shared connector contract for tenant binding, credential reference, read-only mode, schema/capability discovery, paginated extraction, checkpointing, idempotent retries, rate limiting, health state, and audit events; implement and test each vendor/source adapter separately.
- **[NEW] Source registration and credentials:** customer admin proposes/configures a source within their tenant. Store secrets in a protected secret facility (selection/integration is **[DECISION]**, not established by FACTS); never store them in connector config, logs or prompts. Operator can rotate or revoke credentials without viewing content. Validate tenant region and source ownership before enabling. Require OpenJM entitlement/platform approval for connector types if that is the chosen operator policy; customer admin retains control of tenant-specific source settings.
- **[NEW] Ingestion modes:** for databases/warehouses, start with read-only schema discovery and explicitly scoped tables/views; use incremental watermarks/change tracking only where the source supports it, otherwise bounded scheduled snapshots. For object storage, enumerate only admin-approved buckets/prefixes and supported document types, track object version/checksum and deletion. ERP access should use vendor-supported read-only APIs/roles, not direct writes. Treat each source's rate/consistency limits as adapter-specific; do not promise uniform incremental semantics.
- **[NEW] Data handling:** normalize records with tenant ID, source ID, source-native key/version, region, ingestion timestamp and classification/authorization metadata. Make ingestion idempotent, detect deletions/tombstones, quarantine malformed/oversize records, and retain job errors sufficient for repair without storing secrets. Store raw or normalized content only in the tenant's region and within a tenant-partitioned namespace; document retention and backup deletion behavior. Preserve source lineage for citations.
- **[DECISION]:** select source-specific extraction formats, supported ERP/warehouse versions, sync cadence, initial backfill limits, schema-change policy and maximum record/document sizes with customers. These are not specified by FACTS.

## 5. Knowledge ingestion and permission-aware retrieval

- **[EXTEND] Existing document path:** retain PDF/DOCX extraction, 25 MB limit, object storage and internal/confidential classification. Add ingestion status, checksum/version deduplication, safe reprocessing, source lineage and deletion propagation. Validate extracted text and handle encrypted, malformed or unsupported files safely.
- **[NEW] Search indexing:** current production search is whole-document PostgreSQL full-text search; there are no chunks, embeddings, vector store or reranker. First extend retrieval with explicit authorization filters and citations while preserving full-text as a fallback. Add chunking/embedding/vector retrieval only after selecting and region-validating a storage/runtime option; this is new architecture and must not be described as deployed. Evaluate hybrid full-text/vector retrieval against a representative corpus before enabling it. Reranking is optional new work, not a prerequisite or existing capability.
- **[NEW] Access metadata:** associate every indexed document/chunk/record with tenant, source, workspace, classification, source ACL/group scope (where available), and version. Recompute/remove index entries on source ACL changes, deletion, reclassification or tenant access changes. If source permissions cannot be represented faithfully, limit ingestion to an explicitly approved scope and disclose that constraint; do not silently widen access.
- **[EXTEND] Retrieval sequence:** authenticate user; resolve tenant and roles; derive authorized workspaces, source scopes and allowed classification; apply all filters in the retrieval query before content is returned to the answer composer; retrieve bounded evidence; re-check access/version before responding if authorization may have changed during the request; provide citations to the exact document/record version. Never retrieve broadly and rely on the LLM to hide unauthorized results.
- **[NEW] Answer behavior:** pass only the minimum authorized evidence to the LLM; require structured source references grounded in retrieved evidence; validate that cited references belong to the authorized result set; abstain or state uncertainty when evidence is absent, conflicting, stale or below a validated confidence threshold. Confidence thresholds and evaluation method are **[DECISION]** and require acceptance data; an LLM's self-reported confidence alone is not proof.
- **[NEW] Structured data answering:** distinguish SQL/data results from document evidence; show source and query scope, and enough query provenance to reproduce the result without exposing credentials. Enforce row/column restrictions before execution and results composition. **[DECISION]** whether row-level source ACLs and sensitive-column policies must be imported is unresolved; if required, implement them before production access to affected data, since current authorization has no such capability.

## 6. Classification and role enforcement

- Existing document classes are `internal` and `confidential`; confidentiality is an access rule, not just a retrieval ranking or prompt instruction. **[EXTEND]** enforce `confidential` as tenant-admin-only regardless of workspace membership; `viewer` and `analyst` must never receive confidential content or derived snippets/answers. `admin` is tenant-scoped and does not imply operator privileges. Preserve Keycloak's existing viewer < analyst < admin hierarchy; platform-operator roles remain separate and invisible to customer realms.
- **[EXTEND]** perform authorization in trusted application services for every document/source query, citation, export, preview, API and cached result. UI hiding is not enforcement. On group/role/workspace/classification changes, invalidate relevant caches and refresh/revoke derived index permissions promptly; fail closed on missing or malformed claims.
- **[NEW]** classify imported records/documents before making them searchable. Map source-native labels/ACLs to the two existing classes only via an explicit, reviewed mapping; do not invent extra classifications or infer that all data is `internal`. Quarantine unmapped/high-risk content until a customer admin (and, where platform policy requires, operator) resolves it. Define a content handling and reclassification procedure with an audit trail.
- **[DECISION]** existing facts define only internal/confidential. Any further sensitivity levels, column masking, attribute-based policy, per-document user ACL or automated classification require explicit requirements and new policy machinery; until built, scope sources to what the current model can protect.

## 7. Tenant isolation

- **[EXTEND]** carry and validate tenant identity end-to-end from OIDC request through APIs, jobs, connector credentials, object keys, database queries, indexes, caches, exports and telemetry. Continue application-level row scoping and expand tests to every new path. Do not trust tenant IDs supplied in request bodies or source records; derive tenant from authenticated context and bind background jobs to an immutable tenant context.
- **[NEW]** partition or namespace source credentials, raw/normalized content, search indexes, embeddings if added, temporary files and backups by tenant and region. Enforce tenant predicates at storage/retrieval boundaries, not just UI or model prompts. Prevent cross-tenant cache-key collisions; never share retrieval results or train/fine-tune on customer data across tenants.
- **[EXTEND]** operator endpoints expose lifecycle, configuration metadata and usage but no content; customer admin endpoints enforce tenant ownership. Use negative authorization tests with forged IDs across reads, writes, export, search, job status and deletion. Ensure one tenant's long-running or failing job cannot starve another via quotas and isolation controls.
- **[NEW]** tenant export must be tenant-scoped, authenticated, audited and delivered through a region-appropriate protected mechanism. Deletion must remove source-derived content, documents and any embeddings/index copies within 30 days; track completion across replicas, caches, backups and provider retention obligations. Define and verify the deletion boundary for source originals, which remain under source-system ownership unless separately agreed.

## 8. Auditing and operational monitoring

- **[EXTEND] Audit:** retain the append-only audit table for every write and privileged read. Add audit events for source registration/configuration, credential rotation/revocation (never secret values), schema/scope changes, sync/reprocess/pause, group/role/workspace/classification changes, export/deletion requests and completion, tenant suspension, query execution metadata, and operator usage access. Record actor, tenant, action, object, timestamp, outcome and safe details; ensure failed/denied administrative operations are visible. Do not put document bodies, prompts, credentials or query result content in audit detail.
- **[EXTEND] Answer traceability:** persist a protected trace for actionable answers including request/actor/tenant, model/provider and version, authorized source/document IDs and versions, retrieval/query metadata, citation set, and outcome/abstention. Define retention and access for traces; users and support staff must not gain access to other tenants' content through trace inspection.
- **[EXTEND] Monitoring:** add per-connector success/failure, lag, retry, throttling, rows/bytes, extraction errors, index freshness, authorization denials, deletion backlog, export status, LLM latency/errors/token usage and per-tenant quotas to existing structured logs/Prometheus/alerts. Aggregate dimensions to avoid high-cardinality or content leakage. Alert on tenant-boundary errors, unauthorized confidential access attempts, stalled deletion deadlines and region-routing violations; provide runbooks and an incident response path.
- **[CONFIG]/[NEW]** set retention, alert thresholds and on-call/escalation ownership before launch. FACTS states existing logging/metrics capabilities but not retention, alert coverage or SLOs.

## 9. Approval and confirmation boundaries

- **Unattended, after policy/configuration:** read-only scheduled sync of an already approved source and scope; bounded read-only queries that pass authorization/schema/resource checks; document extraction/index updates; retries and quarantine of failed inputs; and answer generation from authorized evidence. Automation may abstain or report an error. No unattended action may grant access, expand scope, change classification policy or alter source data.
- **Customer-admin confirmation, deliberate and audited:** add/change/remove tenant users/groups/roles, workspace/source memberships and permissions; approve a source's tables, views, buckets/prefixes and classification mapping; request export/deletion; reclassify content; and confirm destructive source/index actions. Make changes reversible where technically possible, retain prior configuration/version and support tested rollback.
- **OpenJM operator confirmation, deliberate and audited:** tenant suspension/reactivation, entitlement/platform-policy changes, connector type enablement where controlled centrally, and credential rotation/revocation. Operator controls do not grant content access. Separate operator action from customer data-source authorization.
- **Human escalation/new workflow:** ambiguous or unmappable permissions/classifications, unsupported source semantics, suspicious extraction, unresolved answer/citation evaluation, and any proposed write/action on a source require a human decision. There is no agentic automation or approval workflow framework today; any formal approval UI/state machine is **[NEW]**. This plan does not enable source writes or agentic actions.
- **[NEW]** require explicit approval before sending customer content to a provider unless its region, retention and training treatment have been verified against contract. If no compliant provider/configuration is available, refuse generation rather than route to an unapproved endpoint.

## 10. Testing and acceptance

- **Existing checks:** preserve GitHub Actions build, unit/integration tests, container build and signed release; every merge continues to require review and green checks. Add tests rather than weaken/retarget existing checks.
- **[NEW] Functional tests:** exercise operator tenant lifecycle/usage/credential operations; customer-only user/group/source/permission management; end-user document and structured queries; citations and uncertainty response; export and deletion flows; and the three planes' API/UI boundary.
- **[NEW] Security tests:** tenant A cannot access tenant B through direct IDs, search, citations, job status, exports, caches or background work; operators cannot retrieve content; customers cannot invoke operator controls; viewer/analyst never see confidential content even with workspace membership; admin can access only own-tenant confidential content; revoked membership and reclassification remove access; unauthorized source rows/columns are excluded before model composition. Include fail-closed tests for missing claims, stale policy, connector errors and provider failure.
- **[NEW] Connector/data tests:** vendor/API contract fixtures, pagination, incremental checkpoint replay, duplicate/idempotent ingestion, schema drift, source throttling, credentials rotation, deletion propagation, malformed documents, oversize input, and recovery after partial failure. Test provenance and stale-data disclosure.
- **[NEW] Answer quality/privacy tests:** measure retrieval recall/precision and citation correctness on an approved, tenant-separated test corpus; verify answer abstention for insufficient/conflicting evidence; verify no unsupported answer and no leakage of excluded evidence in answer, logs or traces. Validate provider region/retention settings and confirm no cross-tenant training use contractually/technically.
- **[NEW] NFR/acceptance gates:** agree workload-based latency, freshness, concurrency, cost, availability and recovery objectives before release; run load/failure/isolation tests against those values. Acceptance includes a verified tenant export and deletion of content/index/embedding copies within the contractual 30 days, operator usage view without content, audit completeness, and region-bound processing. Record thresholds and evidence in release artifacts; do not substitute unmeasured claims.

## 11. Deployment and rollback

- **[EXTEND]** deliver via current reviewed CI and signed container release. Release schema changes additively and backward-compatibly; deploy migration, service, connector and UI changes behind per-tenant feature flags/entitlements. Start with internal/non-production fixtures, then a limited consenting tenant/source cohort in its region. Do not enable a connector or LLM route before security, classification and provider-region gates pass.
- **[NEW]** deploy connector workers with tenant-scoped concurrency and quotas; verify secrets, region routing, audit and alerts before scheduling backfills. Use canary syncs and bounded initial snapshots, compare counts/checksums and errors with source expectations, then enable incremental schedules. Roll out retrieval/index changes in shadow or comparison mode where practical; keep the existing full-text path as fallback until quality and permissions pass.
- **Rollback:** disable affected feature flag/schedule and revoke connector credentials; return retrieval to the prior whole-document full-text path where compatible; roll back application image only with backward-compatible schema. Stop new ingestion while preserving a recoverable checkpoint. Revoke/regenerate compromised credentials. If authorization leakage or region breach is suspected, immediately disable affected retrieval/provider path, contain access, preserve audit evidence and follow incident response; do not roll back in a way that restores unauthorized access. Data/index cleanup and migrations need an explicit tested recovery plan.
- **[DECISION]** define deployment topology, backup/restore objectives, migration ownership and rollback windows before production; FACTS gives the current platform but not deployment orchestration or recovery objectives.

## 12. Dependencies, sequencing and bounded work packages

Sequence work so authorization and region handling precede ingestion at scale. Each package has an exit gate; do not make a later package a production dependency until its gate passes.

1. **WP0 — decisions and threat model (bounded discovery):** inventory target vendors, source ACL/schema capabilities, regions, supported provider terms, data classes, workload/SLO/cost targets and export/deletion semantics. Output signed decisions, data-flow map and acceptance thresholds. Blocks production source onboarding. **[DECISION]**
2. **WP1 — policy/tenant foundation (extension):** specify API authorization matrix across three planes; extend tenant-context propagation, audit events and tests; enforce confidential-admin-only and revocation/cache invalidation across all current document routes. Exit: isolation/classification negative tests pass. **[EXTEND]**
3. **WP2 — connector framework and first source adapters (new):** source registry, secret integration, read-only credentials, checkpoint/health contracts, customer admin controls, operator lifecycle/usage view; implement vendor adapters in prioritized, individually bounded increments. Exit: source contract and tenant/region isolation tests pass before pilot. **[NEW]**
4. **WP3 — ingestion and lifecycle (extension/new):** normalize/provenance metadata, idempotent sync, failure recovery, object/document ingestion changes, deletion/export tracking and regional storage. Exit: replay/deletion/export acceptance demonstrated on representative fixtures. **[EXTEND]/[NEW]**
5. **WP4 — permission-aware knowledge retrieval (extension/new):** authorized filtering before composition, exact citations and abstention; compare baseline full-text and selected new chunk/embedding option only after separate technology decision. Exit: ACL, citation, retrieval quality and privacy gates pass. **[EXTEND]/[NEW]**
6. **WP5 — structured-data Q&A (new):** schema catalog, constrained read-only query planner/executor, query budgets, row/column policy hooks and result provenance. Pilot only sources/scopes that can be represented by approved permissions. Exit: no-write, scope enforcement, query-resource and answer evidence tests pass. **[NEW]**
7. **WP6 — operations and release hardening (extension/new):** usage metering/quotas, dashboards/alerts/runbooks, provider-region validation, load/failure tests, canary/rollback and customer/operator training. Exit: defined NFR and contractual acceptance gates pass; signed release and staged tenant enablement. **[EXTEND]/[NEW]**

**Cross-cutting dependencies:** source permission fidelity and classification mapping must be resolved before each source is searchable; tenant/region and secret controls precede any production connector; provider/privacy approval precedes LLM transmission; export/deletion validation precedes customer production data; audit and observability ship with each control, not as post-launch cleanup. Configuration-only changes are limited to supported existing roles/workspaces, the existing REST connector, and existing monitoring/CI settings; all other listed connector, fine-grained permission, vector/embedding, structured-query, provider-governance and approval capabilities require explicit build/selection work.


### FACTS.md
# FACTS.md — what exists today, and what is contractually required

Authoritative for T1. If a plan needs something outside this list, it must say so explicitly
instead of assuming it exists.

## Deployed and working (production)

- Multi-tenant SaaS on Ubuntu 24.04, PostgreSQL 16.15, Keycloak 26.7.4 for SSO, Node 22 and
  Python 3.11 services, deployed as a non-root `openjm` user.
- Every request carries a tenant claim; row-level tenant scoping is enforced in application
  code and covered by tests. Customer data for one tenant is never visible to another.
- Keycloak realms per tenant, OIDC with PKCE, group-to-role mapping: roles are
  `viewer` < `analyst` < `admin`, plus platform-operator roles that customers never see.
- An audit table records actor, tenant, action, object and detail for every write and every
  privileged read; audit rows are append-only.
- Workspaces: a named container that groups a customer's folders and resources. Workspace
  membership is the coarse authorization unit today.
- Document ingestion for PDF/DOCX up to 25 MB into object storage, with text extraction and
  a per-document classification of `internal` or `confidential`. Chunking and embeddings are
  **not** in production.
- A retrieval service that searches **whole documents** with PostgreSQL full-text search,
  filtered by workspace membership; there is no vector store in production.
- Connectors: a REST source connector for JSON APIs. No ERP, warehouse, SQL Server or
  object-storage connectors exist yet.
- Operational monitoring: structured logs, Prometheus metrics for request latency and error
  rates, and an alert on failed background jobs.
- CI: GitHub Actions with build, unit and integration tests, a container build and a signed
  release; every merge requires review and green checks.

## Contractual and business requirements

- Customer data stays within the customer's region; no cross-tenant training, no cross-tenant
  retrieval. A tenant administrator can request a data export; a deletion request must remove
  content and embeddings within 30 days.
- Every answer that a user can act on must be traceable to the sources it used, and answers
  that the system is not confident about must say so rather than guess.
- Confidential documents are readable only by tenant administrators, never by `viewer` or
  `analyst`, regardless of workspace membership.
- The operator plane must be able to suspend a tenant, rotate a connector credential and see
  per-tenant usage without being able to read customer content.
- Customer administrators manage their own users, groups and data sources, and cannot see or
  change anything belonging to another customer.
- Administrative changes to access must be deliberate, audited, and reversible.

## Explicitly not available

- No vector database, no embedding pipeline, no reranking in production.
- No ERP (SAP/NetSuite/Dynamics), data-warehouse (Snowflake/BigQuery/Redshift), SQL Server or
  object-storage connector.
- No policy engine beyond Keycloak roles and workspace membership; no document-level ACLs
  beyond the `internal`/`confidential` classification.
- No managed LLM gateway: model access is per-provider API keys today.
- No agentic automation in the product; there is no approval workflow framework to reuse.


### plan-assumptions.md
# Plan assumptions

These are planning assumptions, not facts established by FACTS.md. Validate them in WP0 before committing to implementation. Unresolved options are identified as decisions in `plan.md`.

- Initial source access is read-only. The business asks employees to query sources, and FACTS states there is no agentic automation; therefore the proposed first release does not write to ERP, warehouse, database or object-storage sources. Any write use case is out of scope until separately specified and approved.
- Existing deployed application services, Keycloak realms/roles, PostgreSQL, object storage, audit table, CI and monitoring are the platform to extend rather than replace. The precise deployment/orchestration topology is not assumed.
- “Customer data stays within the customer's region” applies to source-derived content, indexes/embeddings if introduced, backups, logs/traces that could contain customer data, and any LLM processing. Confirm contractual interpretation and provider availability before routing content.
- Customer administrators may approve only data scopes their organization is entitled to expose; their source-system permissions and OpenJM entitlements are not interchangeable. Source-specific authorization fidelity must be verified before making imported data searchable.
- The current `internal` and `confidential` classes are the only established classes. No automatic classification, additional labels, source-native ACL equivalence, column masking or per-document ACL capability is presumed to exist.
- Source vendors, versions, supported APIs, source-side credentials, sync frequency, volumes, customer regions, performance/availability/cost targets, secret-management facility, LLM providers and retention settings are not specified. The plan intentionally leaves these as WP0 decisions rather than inventing values or capabilities.
- A vector database, embedding model/pipeline, reranker, managed LLM gateway, and formal approval workflow are not selected or assumed to exist. Any such component requires a separate selection/security review and implementation before use.
- Deletion within 30 days is interpreted to cover OpenJM-held content and derived copies (including indexes and embeddings if introduced); the source system's original records remain controlled by its owner unless a separate agreement says otherwise. Backup and provider deletion semantics must be verified against the commitment.
